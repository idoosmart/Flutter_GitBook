IDO SDK Usage Guide

IDO SDK Usage Guide (protocol_lib and flutter_bluetooth)

1. Document Purpose

This document outlines the integration methods, responsibility boundaries, call flows, and typical usage of protocol_lib and flutter_bluetooth.

For a complete runnable sample, see Flutter_Demo. The sections below cover responsibilities, initialization, bridging, and call order only—they do not bind to specific source files.

Libraries:

  • protocol_lib
  • flutter_bluetooth

Example local path dependencies in pubspec.yaml (use Flutter_Demo as the source of truth for the full project):

protocol_lib:
  path: <file relative path>
protocol_alexa:
  path: <file relative path>
flutter_bluetooth:
  path: <file relative path>

The focus of this document is not the Flutter UI pages themselves, but:

  1. What each library is responsible for
  2. How they are initialized
  3. How they form a complete data closed-loop via bridging
  4. How the UI layer should invoke their capabilities

2. Responsibility Division Between the Two Libraries

2.1 Responsibilities of flutter_bluetooth

flutter_bluetooth is the Bluetooth transport layer, responsible for:

  • Registering the Bluetooth SDK
  • Obtaining Bluetooth status
  • Scanning for devices
  • Connecting / disconnecting devices
  • Writing BLE / SPP data
  • Receiving raw byte streams reported by devices
  • Reporting Bluetooth state, connection state, write state, and scan results

The library exports a global entry; see Flutter_Demo.

Global singleton entry:

final bluetoothManager = IDOBluetoothManager();

2.2 Responsibilities of protocol_lib

protocol_lib is the protocol business layer, responsible for:

  • Registering the protocol library
  • Maintaining the protocol context of the currently connected device
  • Handling protocol state transitions after device connection/disconnection
  • Sending protocol commands
  • Parsing data returned by devices
  • Providing high-level capabilities such as binding, device info, function tables, data synchronization, file transfer, message icons, device logs, and photo watch faces

The library exports a global entry; see Flutter_Demo.

Global singleton entry:

final libManager = IDOProtocolLibManager();

2.3 Boundaries Between the Two Libraries

These two libraries are not mutually replaceable peers, but operate in a layered upper/lower relationship:

  • flutter_bluetooth is responsible for "sending bytes to the device and receiving bytes back from the device."
  • protocol_lib is responsible for "deciding which protocol packets to send, how to parse returned packets, and how to organize business capabilities."

In principle, the UI layer should neither assemble raw BLE bytes manually nor parse device protocol data directly. Instead, pages should:

  • Use flutter_bluetooth for scanning and connecting
  • Use protocol_lib for binding, querying, configuring, syncing, file transfers, and photo watch face installation

3. Core Architecture of demo

The core logic of demo is concentrated in app startup and bridge setup (see Flutter_Demo).

Upon app launch, the following sequence is executed:

  1. runApp(const MyApp())
  2. registerProtocolSDK()
  3. registerBluetoothSDK()
  4. registerProtocolAlexa()
  5. bridgeConnect()

Corresponding code:

void main() async {
  runApp(const MyApp());

  await registerProtocolSDK();
  await registerBluetoothSDK();
  await registerProtocolAlexa();
  await bridgeConnect();
}

3.1 Overall Architecture

Flutter Demo UI
  ├── flutter_bluetooth     scan / connect / BLE·SPP I/O
  └── protocol_lib          parse / command orchestration / bind / sync / file transfer
        └── Smart device

Data flow:
  flutter_bluetooth raw bytes ------------> protocol_lib
  protocol_lib packets to send -----------> flutter_bluetooth write

3.2 Startup Phase Flow

  1. App launch
  2. Register protocol_lib
  3. Register flutter_bluetooth
  4. Register protocol_alexa (if needed)
  5. Establish Bluetooth and protocol bridge
  6. Request permissions on the home page
  7. Start scanning devices
  8. User selects a device
  9. Initiate Bluetooth connection
  10. On success, call markConnectedDeviceSafe(...)
  11. Page can run bind / sync / set / get

Important: markConnectedDeviceSafe(...) and markDisconnectedDevice(...) are critical lifecycle entry points for connecting a device to protocol_lib, and MUST be used in pairs.

You must strictly adhere to this rule:

  • After Bluetooth connection succeeds, call markConnectedDeviceSafe(...)
  • After Bluetooth disconnects, connection is actively canceled, or system Bluetooth is turned off, call markDisconnectedDevice(...)

If you only call the former without the latter, protocol_lib may retain an erroneous online state indefinitely.
If you only call the latter without the former, protocol_lib will fail to establish the protocol context for the current device.

4. Startup and Initialization Flow

4.1 protocol_lib Initialization

demo initializes the protocol library inside registerProtocolSDK():

await IDOProtocolLibManager.register(outputToConsole: true);
libManager.messageIcon.registerListenUpdate();
libManager.listenDeviceNotification((event) {
  print('listenDeviceNotification: ${event.toMap().toString()}');
});

4.1.1 Role of register(...)

IDOProtocolLibManager.register(...) is a mandatory entry point before using the protocol layer. It performs:

  • Initializing the protocol logging system
  • Initializing local KV storage
  • Initializing the C library / protocol runtime environment

Common parameters:

  • outputToConsole
    • Whether to output SDK logs to the console
  • outputToConsoleClib
    • Whether to output C library logs to the console
  • isReleaseClib
    • Whether to run the C library in release mode

In demo, only outputToConsole: true is enabled.

4.1.2 Immediate Actions After Initialization

Immediately after registering the protocol library, demo performs two actions:

  1. libManager.messageIcon.registerListenUpdate()
  2. libManager.listenDeviceNotification(...)

Notes:

  • The first item registers a listener for iOS message icon updates.
  • The second item listens for proactive notifications / control events reported by the device.

While not every project must copy these listeners verbatim, they are integrated as part of protocol-layer initialization in the demo.

4.2 flutter_bluetooth Initialization

demo initializes the Bluetooth library inside registerBluetoothSDK():

await bluetoothManager.register();
final version = bluetoothManager.getSdkVersion();

4.2.1 Role of register(...)

During registration, the Bluetooth library performs the following:

  • Initializes logging
  • Registers platform channels
  • Starts the iOS heartbeat mechanism
  • Proactively queries Bluetooth state
  • Listens to Bluetooth state changes
  • Listens to device connection states
  • Listens to incoming data
  • Listens to scan results

In other words, bluetoothManager.register() is not just a "simple initialization"—it begins managing the Bluetooth state streams immediately.

4.2.2 getSdkVersion()

The demo retrieves the Bluetooth SDK version number without displaying it in the UI. This call is primarily useful for:

  • Debugging
  • Log reporting
  • Quickly verifying the integrated SDK version

4.3 protocol_alexa Initialization

Although this guide focuses on the first two libraries, demo also registers Alexa:

await IDOProtocolAlexa.register(clientId: clientId);
Connectivity().onConnectivityChanged.listen((event) {
  IDOProtocolAlexa.onNetworkChanged(hasNetwork: event != ConnectivityResult.none);
});

While peripheral to the main topic here, this highlights an architectural fact:

  • protocol_lib and flutter_bluetooth form the core device communication pipeline.
  • protocol_alexa is a business extension module built on top of device capabilities.

5. Bridging Between the Bluetooth Layer and Protocol Layer

This is the most critical part of the demo: the bridgeConnect() bridge (see Flutter_Demo).

Without this bridge:

  • flutter_bluetooth can only connect to devices, send bytes, and receive bytes.
  • protocol_lib has no way of knowing when a device connects, nor can it receive data returned via Bluetooth.

Once bridged, the two libraries form a complete closed loop.

5.1 Bridging Relationship Overview

App / UI                         SDK / device
 |                                |
 |-- connect(device) ------------>|   flutter_bluetooth
 |                                |-- establish BLE ------> device
 |                                |<- connected -----------|
 |-- markConnectedDeviceSafe ---->|   protocol_lib
 |                                |
 |-- send() / bind() / startSync ->|
 |                                |-- write packets -------> device
 |                                |<- raw bytes ------------|
 |<- CmdResponse / BindStatus ----|
 |   / SyncData                   |

5.2 Passing Data Received by Bluetooth to the Protocol Layer

Demo implementation:

bluetoothManager.receiveData().listen((event) {
  if (event.data != null) {
    libManager.receiveDataFromBle(
      event.data!,
      event.macAddress,
      event.spp ?? false ? 1 : 0,
    );
  }
});

Notes:

  • receiveData() is the raw packet entry stream of the Bluetooth library.
  • receiveDataFromBle(...) is the main packet ingestion entry point of the protocol library.

Parameter meanings:

  • event.data!
    • Raw byte data returned by the device
  • event.macAddress
    • Device address associated with the current packet
  • event.spp ?? false ? 1 : 0
    • Data channel type:
    • 0 indicates BLE
    • 1 indicates SPP

5.2.1 Why This Step Is Critical

Only when libManager.receiveDataFromBle(...) is called can the protocol library:

  • Parse response packets
  • Trigger callbacks for corresponding commands
  • Update device info, function tables, and sync states
  • Trigger listenStatusNotification(...)
  • Trigger callbacks for high-level modules such as binding, syncing, file transfers, and data exchange

If this bridge is missing, the UI will exhibit the following symptoms:

  • Connection succeeds
  • Sending appears to succeed
  • None of the protocol capabilities ever fire callbacks

5.3 Passing Data to Send from the Protocol Layer to the Bluetooth Layer

Demo implementation:

IDOBluetoothWriteType rs = IDOBluetoothWriteType.withoutResponse;
libManager.registerWriteDataToBle((event) async {
  rs = await bluetoothManager.writeData(event.data, type: event.type);
  if (rs == IDOBluetoothWriteType.withoutResponse && Platform.isIOS) {
    libManager.writeDataComplete();
  }
});

Notes:

  • registerWriteDataToBle(...) registers an "actual packet transmission function" with the protocol library.
  • Whenever the protocol library has a command to send, it passes a CmdRequest to the business layer via this callback.
  • The demo then invokes bluetoothManager.writeData(...) to transmit the data to the device.

Parameter meanings:

  • event.data
    • Byte stream already assembled by the protocol library ready for transmission
  • event.type
    • Write type:
    • 0 for BLE
    • 1 for SPP

5.3.1 Why the UI Layer Should Not Assemble Packets Manually

Because protocol_lib already encapsulates:

  • Command queuing
  • Request payload encoding
  • Priority handling
  • State management
  • Timeouts and task coordination

The UI/bridge layer only needs to transmit the "bytes provided by the protocol library" and should never bypass protocol_lib to construct raw packets directly.

5.4 Write Completion Confirmation Callbacks

The demo handles two scenarios:

5.4.1 iOS Write Without Response

if (rs == IDOBluetoothWriteType.withoutResponse && Platform.isIOS) {
  libManager.writeDataComplete();
}

Reason:

  • On iOS, writing without response does not return a separate explicit completion event like writing with response does.
  • Therefore, immediately after writeData(...) returns, the protocol library is notified that the transmission is complete.

5.4.2 Android or Write With Response

bluetoothManager.writeState().listen((event) {
  if (event.state ?? false) {
    if (Platform.isAndroid || event.type == IDOBluetoothWriteType.withResponse) {
      libManager.writeDataComplete();
    }
  }
});

Purpose:

  • Notifies the protocol library to continue scheduling the command queue once the Bluetooth library confirms a write operation has completed.

5.4.3 Consequences of Not Calling writeDataComplete()

The protocol library will assume the current command has not finished underlying transmission, resulting in:

  • Queue blocking
  • Subsequent commands failing to dispatch
  • Behavior where "only the first packet is sent, and everything after stalls"

6. Bluetooth Scanning and Device Selection Flow

Bluetooth scanning and device-list UI logic is in Flutter_Demo.

6.1 Permission and Bluetooth Switch Checks

Tapping the bottom-right button on the home page invokes requestPermission().

On Android, demo performs the following checks:

  1. Checks location permissions on Android 29 and above
  2. Checks if the Bluetooth switch is turned on
  3. Requests Permission.bluetoothScan
  4. Requests Permission.bluetoothConnect
  5. Calls bluetoothManager.startScan()

6.1.1 Why Location Permission Is Checked First

This is a standard prerequisite for Bluetooth scanning on Android. demo explicitly checks for Android 29+:

  • If location permission is denied, an error prompt is displayed.
  • Scanning does not proceed.

6.2 Starting a Scan

The demo directly calls:

bluetoothManager.startScan();

According to the Bluetooth library implementation, startScan([String? macAddress]) supports:

  • Scanning all nearby devices when no argument is provided
  • Scanning for a specific device when macAddress is provided

Before scanning, the Bluetooth library internally:

  • Checks Bluetooth status
  • Stops any active scan
  • Clears partial scan caches
  • Starts native-side scanning

6.3 Receiving Scan Results

The home content widget listens to scan results in initState():

bluetoothManager.scanResult().listen((event) {
  setState(() {
    devices = event;
  });
});

This returns:

Stream<List<IDOBluetoothDeviceModel>>

The page renders each device as a button displaying:

  • device.name
  • device.macAddress

6.4 Selecting a Device

Tapping a device triggers:

Navigator.push(context, MaterialPageRoute(builder: (context)=>FunctionIndex(device)));

Key design detail:

  • The page passes the IDOBluetoothDeviceModel object returned from the scan results.
  • Subsequent connection calls pass this exact object directly into bluetoothManager.connect(device).

This is crucial because the scanned device object already contains vital metadata:

  • macAddress
  • uuid
  • deviceId
  • platform
  • isOta
  • isTlwOta

In particular, the iOS uuid is required later when registering the connected device with the protocol layer.

7. Post-Connection Handling Flow

Connection logic is in Flutter_Demo.

Important: The most crucial takeaway in this chapter is not how to wire up the connect button, but rather:

  • Call markConnectedDeviceSafe(...) after a connection succeeds
  • Call markDisconnectedDevice(...) after a connection ends

These two methods MUST be invoked in pairs.

7.1 Initiating and Canceling Connection

On the function page, tapping the "Connect" button calls:

bluetoothManager.connect(device);

To disconnect:

bluetoothManager.cancelConnect();

7.2 Listening to Bluetooth Connection State

demo listens to bluetoothManager.deviceState() in two places (see Flutter_Demo):

  • Global bridge: synchronizes connection/disconnection states with the protocol layer
  • Function page: updates UI state, such as enabling or disabling the "Connect / Bind / Sync / Alexa" buttons

7.3 Notifying the Protocol Layer After Bluetooth Connection Succeeds

Important: markConnectedDeviceSafe(...) is not a mere notification—it is the key action that transitions protocol_lib into its "Device Online Protocol State."

It MUST be maintained as a pair with markDisconnectedDevice(...).

Bridge code:

if ((value.state == IDOBluetoothDeviceStateType.connected &&
    (value.macAddress != null && value.macAddress!.isNotEmpty))) {
  final isTlwOta = bluetoothManager.currentDevice?.isTlwOta ?? false;
  final isOta = bluetoothManager.currentDevice?.isOta ?? false;
  final otaType = isTlwOta
      ? IDOOtaType.telink
      : isOta
          ? IDOOtaType.nordic
          : IDOOtaType.none;

  final devicenName = bluetoothManager.currentDevice?.name;
  var uniqueId = value.macAddress!;

  if (Platform.isIOS && bluetoothManager.currentDevice?.uuid != null) {
    uniqueId = bluetoothManager.currentDevice!.uuid!;
  }

  await libManager.markConnectedDeviceSafe(
      uniqueId: uniqueId,
      otaType: otaType,
      isBinded: false,
      deviceName: devicenName);
}

7.3.1 Significance of markConnectedDeviceSafe(...)

This method is the key trigger for bringing the protocol layer into an online state.

Important: You can think of markConnectedDeviceSafe(...) as telling protocol_lib: "The current device is officially online; establish the protocol context now."

Once called, the protocol library knows:

  • Which device is currently connected
  • The unique identifier of the current device
  • Whether the current device is in OTA mode
  • The name of the current device
  • Whether the current device is bound

If omitted, even though Bluetooth is physically connected, protocol_lib will continue to believe no device is attached.

Pay special attention to this distinction:

  • Calling bluetoothManager.connect(...) does NOT mean protocol_lib is connected to the device.
  • Only after calling markConnectedDeviceSafe(...) does protocol_lib enter an operational state.

7.3.2 uniqueId Selection Strategy

As noted in the source comments:

  • Android: Pass the connected device's macAddress.
  • iOS: Prefer passing uuid (though macAddress or uuid is accepted).

demo handles this by:

  • Defaulting to macAddress.
  • Overriding with uuid if running on iOS and uuid is available.

7.3.3 Origin of otaType

demo reads the following flags from bluetoothManager.currentDevice:

  • isTlwOta
  • isOta

And maps them to the IDOOtaType enum required by the protocol library:

  • telink
  • nordic
  • none

7.3.4 Handling isBinded in demo

The current demo has been updated to restore the binding state from the app's own persistent storage rather than relying directly on libManager.cache.

The page-level listener handles it as follows:

final isBinded = await BindStateStorage.load(event.macAddress!);
await libManager.markConnectedDeviceSafe(
  uniqueId: uniqueId,
  otaType: otaType,
  isBinded: isBinded,
);

The corresponding persistence wrapper uses SharedPreferences (see Flutter_Demo).

In a production app, the recommended best practice is:

  • Restore the device's binding status from your app's local persistence or backend system.
  • Pass that status into the protocol layer.
  • Do not treat the protocol library's internal cache as your app's single source of business truth.

7.4 Notifying the Protocol Layer After Device Disconnection

Important: markDisconnectedDevice(...) is not an optional cleanup—it is the critical action that transitions protocol_lib out of its "Device Online Protocol State."

It MUST appear as a pair with markConnectedDeviceSafe(...).

In demo, when the Bluetooth state transitions to disconnected, it calls:

await libManager.markDisconnectedDevice(
    macAddress: value.macAddress, uuid: value.uuid);

Similarly, when the phone's system Bluetooth is turned off, it calls:

await libManager.markDisconnectedDevice(
    macAddress: macAddress, uuid: uuid);

This step serves to:

  • Clean up the protocol online state
  • Prevent pages from continuing to invoke online-only capabilities
  • Avoid the protocol library mistakenly assuming the device is still reachable

Pay close attention to this distinction as well:

  • Disconnecting at the Bluetooth library level does NOT automatically take protocol_lib offline.
  • Only after calling markDisconnectedDevice(...) does protocol_lib complete protocol teardown.

7.4.1 Paired Usage Rule

Important: We strongly recommend adding these two rules to your project's integration guidelines:

  1. Every valid connection established MUST be followed by one call to markConnectedDeviceSafe(...).
  2. Every connection lifecycle termination MUST be followed by one call to markDisconnectedDevice(...).

The safest approach is to centralize both calls inside the global Bluetooth state listener rather than scattering them across UI button handlers.

9.9.1 Binding State Persistence

In the current demo, upon successful binding, the state is saved to app-local storage:

Upon successful unbinding, this persisted state is cleared:

  BindStateStorage.clear(libManager.macAddress);
}

If unbindOnBindStateError occurs, demo first clears the app-side record before executing a forced unbind, preventing mismatches between the app's record and the device's actual state.

9.9.2 Internal Binding Flow Overview

  1. Checks libManager.isConnected

  6. Fetches the function table
  7. Invokes the functionTable(...) callback
  8. Emits the corresponding BindStatus based on the device's response

11. Recommended Integration Sequence

If you are migrating demo's architecture into your own project, follow this sequence.

11.1 Minimal Integration Order

  1. Add protocol_lib and flutter_bluetooth dependencies.
  2. On app startup, initialize both libraries:
    • IDOProtocolLibManager.register(...)
    • bluetoothManager.register()
  3. Set up the data bridge:
    • receiveData() -> receiveDataFromBle(...)
    • registerWriteDataToBle(...) -> writeData(...)
    • writeState() -> writeDataComplete()
  4. Implement Bluetooth scanning and device selection.
  5. Call markConnectedDeviceSafe(...) upon Bluetooth connection success.
  6. Call markDisconnectedDevice(...) upon Bluetooth disconnection.
  7. Persist the device binding state on the app side.
  8. Invoke binding, querying, settings, and syncing via libManager, and photo watch faces via IDODialManager().dialPhoto.

Important: Steps 5 and 6 MUST be implemented as a pair—never implement one without the other.

11.2 Recommended Integration Flow

Add dependencies
  -> Register protocol_lib
  -> Register flutter_bluetooth
  -> Establish write-data bridge
  -> Establish receive-data bridge
  -> Scan devices
  -> Connect device
       |-- markConnectedDeviceSafe -> Bind device
       |                              -> Get / set / sync / file transfer
       `-- Disconnect --------------> markDisconnectedDevice

14. Summary

The core integration philosophy of demo can be summarized in one sentence:

  • flutter_bluetooth handles connecting to devices and sending/receiving raw bytes.
  • protocol_lib handles protocol lifecycles, commands, binding, synchronization, photo watch faces, and business encapsulation.
  • Bridging logic ties the two together into a complete device communication pipeline (see Flutter_Demo).

Therefore, the most reliable integration pattern is not having UI pages emit raw Bluetooth packets directly, but rather:

  1. Establish the connection via the Bluetooth library.
  2. Hand over the device context to the protocol library.
  3. Invoke high-level protocol business APIs from the UI layer.
  4. Let the protocol library transmit and receive underlying bytes through the Bluetooth library.

Important: The single most important rule to remember from this entire document:

  • markConnectedDeviceSafe(...) and markDisconnectedDevice(...) are the critical lifecycle entry points for protocol_lib.
  • They MUST always be implemented as a pair.
  • They correspond to protocol online initialization and protocol offline teardown, respectively.
