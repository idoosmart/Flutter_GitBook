IDO SDK 使用流程说明

IDO SDK 使用流程说明（protocol_lib 与 flutter_bluetooth）

1. 文档目的

本文梳理 protocol_lib 与 flutter_bluetooth 的接入方式、职责边界、调用流程与典型用法。

完整可运行示例请对照 Flutter_Demo。下文只说明职责、初始化、桥接与调用顺序，不绑定具体源码文件。

依赖库：

  • protocol_lib
  • flutter_bluetooth

pubspec.yaml 本地依赖示意（完整工程依赖以 Flutter_Demo 为准）：

protocol_lib:
  path: <file relative path>
protocol_alexa:
  path: <file relative path>
flutter_bluetooth:
  path: <file relative path>

本文重点不是解释 Flutter 页面本身，而是说明：

  1. 这两个库分别负责什么
  2. 它们如何被初始化
  3. 它们如何通过桥接形成完整的数据闭环
  4. 页面层应该如何调用它们的能力

2. 两个库的职责划分

2.1 flutter_bluetooth 的职责

flutter_bluetooth 是蓝牙传输层，负责：

  • 注册蓝牙 SDK
  • 获取蓝牙状态
  • 扫描设备
  • 连接 / 断开设备
  • BLE / SPP 数据写入
  • 接收设备上报原始字节流
  • 上报蓝牙状态、连接状态、写入状态、扫描结果

全局入口由库导出，详见 Flutter_Demo。

全局单例入口：

final bluetoothManager = IDOBluetoothManager();

2.2 protocol_lib 的职责

protocol_lib 是协议业务层，负责：

  • 注册协议库
  • 维护当前接入设备的协议上下文
  • 处理设备连接/断开后的协议状态切换
  • 发送协议指令
  • 解析设备返回数据
  • 提供绑定、设备信息、功能表、同步、文件传输、消息图标、日志、照片表盘等上层能力

全局入口由库导出，详见 Flutter_Demo。

全局单例入口：

final libManager = IDOProtocolLibManager();

2.3 两者的边界

这两个库不是并列互相替代，而是上下层关系：

  • flutter_bluetooth 负责“把字节送到设备、把字节从设备拿回来”
  • protocol_lib 负责“决定发什么协议包、如何解析返回包、如何组织业务能力”

页面层原则上不应自己拼装 BLE 原始字节，也不应直接解析设备协议数据。页面应：

  • 用 flutter_bluetooth 做扫描和连接
  • 用 protocol_lib 做绑定、查询、设置、同步、文件传输、照片表盘安装

3. demo 的核心架构

demo 的核心逻辑集中在应用启动与桥接初始化流程中（见 Flutter_Demo）。

应用启动后，按以下顺序执行：

  1. runApp(const MyApp())
  2. registerProtocolSDK()
  3. registerBluetoothSDK()
  4. registerProtocolAlexa()
  5. bridgeConnect()

对应代码：

void main() async {
  runApp(const MyApp());

  await registerProtocolSDK();
  await registerBluetoothSDK();
  await registerProtocolAlexa();
  await bridgeConnect();
}

3.1 总体架构

Flutter Demo UI
  ├── flutter_bluetooth     蓝牙扫描 / 连接 / BLE·SPP 收发
  └── protocol_lib          协议解析 / 指令编排 / 绑定 / 同步 / 文件传输
        └── 智能设备

数据流：
  flutter_bluetooth 收原始字节 -----> protocol_lib
  protocol_lib 生成待发送协议包 ----> flutter_bluetooth 写出

3.2 启动阶段流程

  1. 应用启动
  2. 注册 protocol_lib
  3. 注册 flutter_bluetooth
  4. 注册 protocol_alexa（按需）
  5. 建立蓝牙与协议桥接
  6. 首页申请权限
  7. 开始扫描设备
  8. 用户选择设备
  9. 发起蓝牙连接
  10. 连接成功后调用 markConnectedDeviceSafe(...)
  11. 页面可执行绑定 / 同步 / 设置 / 查询

重要： markConnectedDeviceSafe(...) 和 markDisconnectedDevice(...) 是 protocol_lib 接入设备生命周期的关键入口，必须成对出现。

必须固定遵守这条规则：

  • 蓝牙连接成功后，调用 markConnectedDeviceSafe(...)
  • 蓝牙连接断开、主动取消连接、系统蓝牙关闭后，调用 markDisconnectedDevice(...)

如果只调前者，不调后者，protocol_lib 可能一直保留错误的在线状态。
如果只调后者，不调前者，protocol_lib 则无法建立当前设备的协议上下文。

4. 启动与初始化流程

4.1 protocol_lib 初始化

demo 在 registerProtocolSDK() 中初始化协议库：

await IDOProtocolLibManager.register(outputToConsole: true);
libManager.messageIcon.registerListenUpdate();
libManager.listenDeviceNotification((event) {
  print('listenDeviceNotification: ${event.toMap().toString()}');
});

4.1.1 register(...) 的作用

IDOProtocolLibManager.register(...) 是协议层使用前的必要入口。它会完成：

  • 初始化协议日志系统
  • 初始化本地 KV 存储
  • 初始化 C 库 / 协议运行环境

常用参数：

  • outputToConsole
    • 是否把 SDK 日志输出到控制台
  • outputToConsoleClib
    • 是否把 C 库日志输出到控制台
  • isReleaseClib
    • 是否让 C 库按 release 模式运行

5. 蓝牙层与协议层的桥接

这是整个 demo 最关键的部分：bridgeConnect() 桥接逻辑（见 Flutter_Demo）。

如果没有这层桥接：

  • flutter_bluetooth 只能连设备、发字节、收字节
  • protocol_lib 无法知道设备什么时候连接，也拿不到蓝牙返回的数据

桥接后，两个库才组成完整闭环。

5.1 桥接关系总览

App / UI                         SDK / 设备
 |                                |
 |-- connect(device) ------------>|   flutter_bluetooth
 |                                |-- 建立蓝牙连接 -----> 设备
 |                                |<- connected ----------|
 |-- markConnectedDeviceSafe ---->|   protocol_lib
 |                                |
 |-- send() / bind() / startSync ->|
 |                                |-- 写出协议包 -------> 设备
 |                                |<- 原始数据 ----------|
 |<- CmdResponse / BindStatus ----|
 |   / SyncData                   |

5.2 把蓝牙收到的数据交给协议层

demo 写法：

bluetoothManager.receiveData().listen((event) {
  if (event.data != null) {
    libManager.receiveDataFromBle(
      event.data!,
      event.macAddress,
      event.spp ?? false ? 1 : 0,
    );
  }
});

说明：

  • receiveData() 是蓝牙库的原始收包入口
  • receiveDataFromBle(...) 是协议库的总收包入口

参数含义：

  • event.data!
    • 设备返回的原始字节数据
  • event.macAddress
    • 当前包对应设备地址
  • event.spp ?? false ? 1 : 0
    • 数据通道类型
    • 0 表示 BLE
    • 1 表示 SPP

5.2.1 这一段为什么关键

只有调用了 libManager.receiveDataFromBle(...)，协议库才能：

  • 解析响应包
  • 唤醒对应命令的回调
  • 更新设备信息、功能表、同步状态
  • 触发 listenStatusNotification(...)
  • 触发绑定 / 同步 / 文件传输 / 数据交换等上层模块回调

如果这一段缺失，页面会表现成：

  • 连接成功
  • 发送看似成功
  • 但协议能力全部没有回调

5.3 把协议层要发送的数据交给蓝牙层

demo 写法：

IDOBluetoothWriteType rs = IDOBluetoothWriteType.withoutResponse;
libManager.registerWriteDataToBle((event) async {
  rs = await bluetoothManager.writeData(event.data, type: event.type);
  if (rs == IDOBluetoothWriteType.withoutResponse && Platform.isIOS) {
    libManager.writeDataComplete();
  }
});

说明：

  • registerWriteDataToBle(...) 由协议库注册一个“实际发包函数”
  • 协议库内部一旦有命令需要发送，就通过这个回调把 CmdRequest 抛给业务层
  • demo 再调用 bluetoothManager.writeData(...) 真正发给设备

参数含义：

  • event.data
    • 协议库已经拼装好的待发送字节流
  • event.type
    • 写入类型
    • 0 是 BLE
    • 1 是 SPP

5.3.1 为什么页面层不应自己拼包

因为 protocol_lib 已经封装了：

  • 指令队列
  • 请求体编码
  • 优先级
  • 状态管理
  • 超时与任务协调

页面层只需要负责把“协议库给出的字节”发出去，不应自己绕过 protocol_lib 直接构造包体。

5.4 写入完成后的确认回调

demo 处理了两种情况：

5.4.1 iOS 无响应写

if (rs == IDOBluetoothWriteType.withoutResponse && Platform.isIOS) {
  libManager.writeDataComplete();
}

原因：

  • iOS 无响应写不会像有响应写那样再返回明确完成事件
  • 所以在 writeData(...) 返回后，直接通知协议库“发送完成”

5.4.2 Android 或有响应写

bluetoothManager.writeState().listen((event) {
  if (event.state ?? false) {
    if (Platform.isAndroid || event.type == IDOBluetoothWriteType.withResponse) {
      libManager.writeDataComplete();
    }
  }
});

作用：

  • 当蓝牙库确认一次写入完成后，再通知协议库继续调度命令流程

5.4.3 如果不调用 writeDataComplete()

协议库可能认为当前命令还没有完成底层发送，从而导致：

  • 队列阻塞
  • 后续命令不继续下发
  • 看起来像“只发送第一包，后面都卡住”

6. 蓝牙扫描与设备选择流程

蓝牙扫描与设备列表的页面逻辑见 Flutter_Demo。

6.1 权限与蓝牙开关检查

点击首页右下角按钮后调用 requestPermission()。

demo 在 Android 下做了这些检查：

  1. Android 29 及以上检查定位权限
  2. 检查蓝牙开关是否已打开
  3. 申请 Permission.bluetoothScan
  4. 申请 Permission.bluetoothConnect
  5. 调用 bluetoothManager.startScan()

6.1.1 为什么要先检查定位权限

这是 Android 蓝牙扫描常见前置条件。demo 中对 Android 29+ 做了显式判断：

  • 如果没有定位权限，就弹出错误提示
  • 不继续扫描

6.2 开始扫描

demo 直接调用：

bluetoothManager.startScan();

从蓝牙库实现上看，startScan([String? macAddress]) 支持：

  • 不指定参数时扫描全部设备
  • 指定 macAddress 时扫描指定设备

扫描前蓝牙库内部还会：

  • 检查蓝牙状态
  • 停止已有扫描
  • 清理部分扫描缓存
  • 启动原生侧扫描

6.3 获取扫描结果

首页内容组件在 initState() 中监听：

bluetoothManager.scanResult().listen((event) {
  setState(() {
    devices = event;
  });
});

这里返回的是：

Stream<List<IDOBluetoothDeviceModel>>

页面把每个设备展示为按钮，显示：

  • device.name
  • device.macAddress

6.4 选择设备

点击设备后，调用：

Navigator.push(context, MaterialPageRoute(builder: (context)=>FunctionIndex(device)));

这里有个很重要的设计点：

  • 页面传递的是扫描结果返回的 IDOBluetoothDeviceModel
  • 后续连接时直接用这个对象调用 bluetoothManager.connect(device)

这很重要，因为扫描返回对象里通常已经包含：

  • macAddress
  • uuid
  • deviceId
  • platform
  • isOta

尤其是 iOS 的 uuid，后面协议层接入设备时会用到。

7. 连接设备后的处理流程

连接逻辑见 Flutter_Demo。

重要： 本章最关键的不是“连接按钮怎么写”，而是：

  • 连接成功后要调用 markConnectedDeviceSafe(...)
  • 连接结束后要调用 markDisconnectedDevice(...)

这两个方法必须成对出现。

7.1 发起连接

功能页里，点击“连接”按钮时：

bluetoothManager.connect(device);

断开时：

bluetoothManager.cancelConnect();

7.2 监听蓝牙连接状态

demo 中有两处监听 bluetoothManager.deviceState()（见 Flutter_Demo）：

  • 全局桥接处：负责协议层接入 / 断开同步
  • 功能页中：负责页面状态刷新，比如是否允许“连接 / 绑定 / 同步 / Alexa”按钮可点

7.3 蓝牙连接成功后，通知协议层设备已接入

重要： markConnectedDeviceSafe(...) 不是普通通知，而是 protocol_lib 正式进入“设备在线协议态”的关键动作。

它必须和 markDisconnectedDevice(...) 配对维护。

桥接代码：

if ((value.state == IDOBluetoothDeviceStateType.connected &&
    (value.macAddress != null && value.macAddress!.isNotEmpty))) {
  final isTlwOta = bluetoothManager.currentDevice?.isTlwOta ?? false;
  final isOta = bluetoothManager.currentDevice?.isOta ?? false;
  final otaType = isTlwOta
      ? IDOOtaType.telink
      : isOta
          ? IDOOtaType.nordic
          : IDOOtaType.none;

  final devicenName = bluetoothManager.currentDevice?.name;
  var uniqueId = value.macAddress!;

  if (Platform.isIOS && bluetoothManager.currentDevice?.uuid != null) {
    uniqueId = bluetoothManager.currentDevice!.uuid!;
  }

  await libManager.markConnectedDeviceSafe(
      uniqueId: uniqueId,
      otaType: otaType,
      isBinded: false,
      deviceName: devicenName);
}

7.3.1 markConnectedDeviceSafe(...) 的意义

这个方法是协议层“进入在线状态”的关键。

重要： 可以直接把 markConnectedDeviceSafe(...) 理解为：告诉 protocol_lib，当前设备已经正式上线，可以建立协议上下文。

调用后，协议库才知道：

  • 当前连的是哪台设备
  • 当前设备唯一标识是什么
  • 当前设备是否为 OTA 模式
  • 当前设备名称是什么
  • 当前设备是否已绑定

如果不调用，虽然蓝牙已经连上，但 protocol_lib 仍可能认为当前没有接入设备。

这里要特别注意：

  • 调用 bluetoothManager.connect(...) 不等于 protocol_lib 已经连上设备
  • 只有调用 markConnectedDeviceSafe(...) 后，protocol_lib 才真正进入可用状态

7.3.2 uniqueId 的取值策略

源码注释已经说明：

  • Android：传当前连接设备的 macAddress
  • iOS：优先传 uuid，也可传 macAddress 或 uuid

demo 的实际处理是：

  • 默认用 macAddress
  • 如果是 iOS 且有 uuid，则改用 uuid

7.3.3 otaType 的来源

demo 从 bluetoothManager.currentDevice 上读取：

  • isTlwOta
  • isOta

转换为协议库需要的 IDOOtaType：

  • telink
  • nordic
  • none

7.3.4 isBinded 在 demo 里的处理

当前 demo 已调整为从 app 自己的持久化里恢复绑定状态，而不是直接依赖 libManager.cache。

页面级监听中会这样处理：

final isBinded = await BindStateStorage.load(event.macAddress!);
await libManager.markConnectedDeviceSafe(
  uniqueId: uniqueId,
  otaType: otaType,
  isBinded: isBinded,
);

对应的持久化封装底层使用 SharedPreferences（见 Flutter_Demo）。

这说明在正式项目里，更合理的做法是：

  • 从 app 本地持久化或业务系统恢复设备绑定状态
  • 再把这个状态传给协议层
  • 不要把协议库内部缓存直接当成 app 的业务真相

7.4 设备断开后，通知协议层已离线

重要： markDisconnectedDevice(...) 不是可选清理，而是 protocol_lib 正式退出“设备在线协议态”的关键动作。

它必须和 markConnectedDeviceSafe(...) 成对出现。

demo 中，当蓝牙状态变为 disconnected 时，会调用：

await libManager.markDisconnectedDevice(
    macAddress: value.macAddress, uuid: value.uuid);

同时，在手机蓝牙关闭时，也会调用：

await libManager.markDisconnectedDevice(
    macAddress: macAddress, uuid: uuid);

这一步用于：

  • 清理协议在线状态
  • 阻止页面继续调用在线能力
  • 避免协议库误认为当前设备仍可通信

这里同样要特别注意：

  • 蓝牙库断开了，不代表 protocol_lib 一定已经退出在线态
  • 只有调用 markDisconnectedDevice(...) 后，protocol_lib 才完成协议下线

7.4.1 成对使用规则

重要： 推荐把下面两条写进项目接入规范：

  1. 任意一次有效连接建立后，必须调用一次 markConnectedDeviceSafe(...)
  2. 任意一次连接生命周期结束后，必须调用一次 markDisconnectedDevice(...)

最稳妥的做法是统一放在蓝牙状态监听里，而不是散落在页面按钮逻辑中。

照片表盘页需要从本地选择 zip / 图片，demo 额外依赖：

  • file_picker：选择表盘包与图片
  • path_provider：把 FilePicker 结果落到可读写临时路径（尤其 iOS）
  • path：拼接本地路径

这些依赖已写入工程 pubspec.yaml（以 Flutter_Demo 为准）。

9.12.3 核心 API

通过表盘管理器进入照片表盘模块：

final photoDial = IDODialManager().dialPhoto;

对应能力由 protocol_lib 的 dial 子模块导出。

解析表盘包

选完表盘外壳 zip 后调用 prepare，返回 UI 预设（颜色、位置、功能能力等）：

final preset = await IDODialManager().dialPhoto.prepare(dialName, packagePath);

demo 中选完 zip 后会自动触发 prepare，并加载包内默认背景图 / 预览图。

裁剪图片

用户另选相册图片时，按表盘参考尺寸裁剪：

final cropped = await IDODialManager().dialPhoto.cropSelectedImage(
  dialName: dialName,
  sourcePath: path,
  isPreview: isPreview,
  preset: preset,
);

安装

组装 IDOPhotoDialConfig 后安装：

IDODialManager().dialPhoto.install(
  config,
  onProgress: (prog) {
    // 0~100
  },
  onSuccess: () {
    // 安装成功
  },
  onFailed: (code, msg) {

  },
);

取消 / 清理本地缓存

IDODialManager().dialPhoto.cancelInstall();
await IDODialManager().dialPhoto.clearLocalResources(dialName);

9.12.4 demo 操作流程

功能列表「照片表盘」
  -> 填写 / 确认 dialName
  -> 选择表盘外壳 zip
  -> prepare 解析预设
  -> 确认或更换背景图 / 预览图
  -> 按需调整颜色 / 位置 / 功能
  -> Install
       |-- 成功 -----> 设备更新照片表盘
       `-- 失败/取消 -> 查看日志并重试

页面上的建议操作顺序：

  1. 确认设备已连接、已绑定
  2. 选择表盘外壳 zip（自动 Prepare）
  3. 确认默认背景图，或重新选图并裁剪
  4. 按需调整时间颜色、功能颜色、位置、功能组件
  5. 点击 Install，观察进度与日志

注意： 思澈 / Actions 平台由 SDK 内部按设备信息自动分流，联调页一般不需要手工分支。

9.12.5 与通用文件传输的区别

  • 通用文件传输走 libManager.transFile（传输已有文件）
  • 照片表盘走 IDODialManager().dialPhoto（先解析外壳包与 UI 配置，再制作并安装）

正式项目接入时，应调用照片表盘 API，而不是只把图片当普通文件上传。

10. demo 中的页面可用条件

功能页对按钮可点击状态做了明确限制（见 Flutter_Demo）。

10.1 状态变量

页面维护两个关键状态：

  • isConnected
  • isBinded

并根据这两个状态控制按钮是否可点。

10.2 连接相关

  • 未连接时，允许“连接”
  • 已连接时，允许“断开连接”

10.3 绑定相关

  • 已连接且未绑定，允许“绑定”
  • 已连接且已绑定，允许“解绑”

10.4 业务能力相关

以下页面入口都要求：

  • 已连接
  • 已绑定

包括：

  • Alexa
  • 同步
  • 获取类功能页
  • 设置类功能页
  • 照片表盘

这个设计隐含表达了 demo 的接入原则：

  • 蓝牙连接成功，不代表业务功能可以立刻使用
  • 很多能力需要设备已经完成协议接入并具备绑定状态

11. 建议按什么顺序接入这两个库

如果你要把 demo 中这套逻辑迁移到自己项目，可以按下面顺序做。

11.1 最小接入顺序

  1. 集成 protocol_lib 与 flutter_bluetooth
  2. App 启动时分别调用：
    • IDOProtocolLibManager.register(...)
    • bluetoothManager.register()
  3. 建立桥接：
    • receiveData() -> receiveDataFromBle(...)
    • registerWriteDataToBle(...) -> writeData(...)
    • writeState() -> writeDataComplete()
  4. 做蓝牙扫描与设备选择
  5. 蓝牙连接成功后调用 markConnectedDeviceSafe(...)
  6. 蓝牙断开后调用 markDisconnectedDevice(...)
  7. app 侧持久化记录设备绑定状态
  8. 页面通过 libManager 调用绑定 / 查询 / 设置 / 同步等业务能力；照片表盘通过 IDODialManager().dialPhoto 调用

重要： 第 5 步和第 6 步必须成对实现，不能只做其中一步。

11.2 推荐接入流程

集成依赖
  -> 注册 protocol_lib
  -> 注册 flutter_bluetooth
  -> 建立写数据桥接
  -> 建立收数据桥接
  -> 扫描设备
  -> 连接设备
       |-- markConnectedDeviceSafe -> 绑定设备
       |                              -> 获取 / 设置 / 同步 / 文件传输
       `-- 断开连接 -----------------> markDisconnectedDevice

14. 总结

demo 的核心接入思路可以概括为一句话：

  • flutter_bluetooth 负责连接设备和收发原始字节
  • protocol_lib 负责协议生命周期、指令、绑定、同步、照片表盘与业务封装
  • 桥接逻辑负责把这两者拼成完整设备通信链路（见 Flutter_Demo）

因此，真正稳定的使用方式不是“页面想发什么就直接发蓝牙包”，而是：

  1. 蓝牙库建立连接
  2. 协议库接管设备上下文
  3. 页面调用协议业务 API
  4. 协议库通过蓝牙库发送和接收底层数据

重要： 整篇文档最需要记住的一条：

  • markConnectedDeviceSafe(...) 与 markDisconnectedDevice(...) 是 protocol_lib 使用的关键入口
  • 它们必须成对出现
  • 它们分别对应协议上线与协议下线
